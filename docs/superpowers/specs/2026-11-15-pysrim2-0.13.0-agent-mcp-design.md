# pysrim2 0.13.0: the agent (MCP server) — design

Date: 2026-11-15. Replaces goal 11 of `2026-11-06-pysrim2-0.12.0-desktop-app-design.md`; where the two differ, this document wins.

## Intent

A user should be able to say, in the agent they already use (Claude Code, Codex, Gemini CLI, Cursor, …):

> simulate N15 into a 200 nm SiO2 layer with 1 µm Si behind it. The energy should be 40 keV of the N. Give me the depth profile.

and have it happen: the target and beam are set up, a run starts, and the depth profile appears, in the Results tab of the pysrim2 app when it is open, or as a saved plot and numbers when it is not (for example when logged in over ssh).

pysrim2 provides this as a **good MCP server**, `pysrim2 mcp`. It does not include a chat panel: the conversation happens in the user's own agent. (Decided by Arun: "If we have a good MCP, we don't need it." A chat panel is not planned for a later release either.)

## Goals

1. **One server, any client.** `pysrim2 mcp` is an MCP server over stdio. Any MCP client can start it. Nothing needs an API key, an account with pysrim2, or network access; the agent runs under the user's own account.
2. **Two modes, one tool set.**
   - **App mode:** if the pysrim2 app is open for the same user on the same machine, `pysrim2 mcp` connects to it and drives the window: edits show in the editing tabs, go into the normal undo history, runs appear in Progress and can be stopped there, and plots appear in the Results tab.
   - **Headless mode:** with no app open (e.g. over ssh), the same tools work on `run.yaml` files, start runs through the library, and return results as numbers and saved plot images.
   - The tools, their names and their arguments are the same in both modes; the agent's instructions do not depend on the mode. Each result says which mode answered, so the agent can say "the plot is in the Results tab" or "saved to …/range.png".
3. **Ask first, enforced by pysrim2.** Some actions need the user's OK, and the server, not the agent's good manners, makes sure it is asked (see "Ask first").
4. **Visible and undoable.** Every agent action is recorded in an activity log. In app mode an **Agent activity** panel shows it, and every agent edit is one undo step, labelled as the agent's.
5. **Easy to connect.** A **Connect an agent** dialog in the app (and a docs page) gives the setup for common clients.
6. **Live results, as an option.** A run setting, off by default, that splits a single run into batches so the Results tab updates while the run goes (see "Live updates").
7. **The agent knows pysrim2.** The server gives the agent the pysrim2 skill (instructions and reference).

## Non-goals

- A chat panel inside the app, now or later.
- Network access to the server (no TCP listener on a public interface, no remote control from another machine; an ssh user runs `pysrim2 mcp` on the remote machine itself).
- Supporting several app windows or several users driving one app.

## Anti-goals

- Agent actions that are invisible or cannot be undone (app mode).
- An agent starting a long or machine-filling run, deleting files, or running installer steps without the user saying yes.
- An agent crash, disconnect or a killed `pysrim2 mcp` process stopping or damaging a run.
- The app's runtime or the library pulling in the MCP SDK or Qt when they are not used (the no-Qt rule from AGENTS.md stays).
- Results from an agent-driven run that differ from a scripted run of the same saved setup (except with the live-update option on, see below).

## Ask first

These actions need the user's OK before they happen:

- **Long runs:** a run or scan estimated to take longer than **30 minutes** (decided by Arun).
- **Many workers:** a run or scan that wants more than **half the CPU cores** (decided by Arun).
- **Deleting or replacing anything on disk:** removing runs, clearing the cache, pruning, an export or a save that would replace an existing file the server did not create in this session.
- **Discarding unsaved work in the app:** an agent `new`/`open` while the app's document has unsaved changes (the same case where the app asks the user today). The agent always edits the document open in the window; the app always has one (a new one at start). *(Claude's call.)*
- **Installer steps:** any `pysrim2 install` step. Admin steps are never run by the server, exactly as in the app: their commands are returned for the user to run in a terminal.

Both limits are settings (Settings dialog in the app; the same `settings.json` under the data directory is read in headless mode). Everything else — editing target, beam, run settings and scan, starting runs below the limits, pausing and stopping runs, reading results, making plots — just happens.

**Estimate:** run time comes from the ions-per-second rate the app already remembers per calculation type (`AppSettings.ions_per_s`, `srim/app/runs.py`). With no rate known, use a conservative stand-in from ion count and target size, and treat "no estimate" as needing the OK when the ion count is large. *(Claude's call; the exact stand-in is the builder's.)*

**How the user answers:**

- **App mode:** a dialog in the pysrim2 window says what the agent wants (e.g. "Start a scan: 12 points, about 2 h, 8 of 10 cores") with Allow and Deny. The tool call waits for the answer (with a timeout that counts as Deny). The dialog must not block the window's other work.
- **Headless, client supports MCP elicitation:** the server asks the user through the client's own prompt.
- **Headless, client without elicitation:** the tool refuses and returns what needs the OK and a one-time code bound to exactly that action. The agent asks the user in the chat and, on yes, repeats the call with the code. *(Claude's call. This step trusts the agent to really ask; the document says so in the user docs. A code is single-use, held in memory only (lost when `pysrim2 mcp` restarts; the agent then simply asks again), expires after a few minutes, and only matches the same action: a hash of the tool, its arguments, the setup content and the resolved parallelism.)*
- Every request and answer goes into the activity log.

## Architecture (decided in conversation, details are the builder's)

- **`pysrim2 mcp`** (new CLI subcommand) runs the MCP server over stdio. On start it looks for a running app (a discovery file in the data directory, readable only by the user, naming the app's local socket and a random token). If it finds one and can connect, it is in app mode; otherwise headless. *(Claude's call: the mode is re-checked when the app appears or goes away during a session, so opening the app mid-session switches to app mode for new calls.)*
- **App side:** the app listens on a per-user local socket (Qt's `QLocalServer`: a Unix socket on POSIX, a named pipe on Windows) only while it runs, checks the token, and runs every request on the GUI thread through the same code paths the tabs use (`DocumentModel.edit`, `RunController`, the Results tab). Several MCP clients may connect at once; their requests are handled one at a time. The handshake carries the MCP client's name and version (from the MCP `initialize`) for the activity log. A stale discovery file (app crashed) is detected by a failed connection and ignored. *(Claude's call.)*
- **Runs across a mode switch:** a run started headless stays a folder-managed run: its status, pause and stop keep working through the scan folder in both modes, and the app does not adopt it (the user can open the folder in the app as a finished or running run, read-only). A run the app started is the app's. The existing scan lock keeps two runs out of one folder. *(Claude's call.)*
- **Headless runs survive the agent.** In headless mode a run is started as a detached `pysrim2 scan run` process on its scan folder, so it keeps going if the agent or `pysrim2 mcp` exits. Status is read from the scan folder (`events.jsonl` and the point records); pause/stop go through `control.jsonl`, as the web view does. In app mode runs belong to the app's `RunController`, so the MCP process going away does not matter.
- **Headless setup editing:** the server keeps a current setup per session (opened from or saved to a `run.yaml` the agent names, relative to the server's working directory). Edits change the in-memory setup; saving writes it. Run folders follow the app's rule (`<setup stem>-runs/<UTC stamp>/`). *(Claude's call.)*
- **Packaging:** the server uses the official MCP Python SDK in a new optional extra **`[mcp]`**, also included in `[app]` and `[all]`. The library and the CLI's other commands do not import it. `pysrim2 mcp` without the extra prints how to install it. The app side of the bridge needs no MCP SDK. *(Claude's call.)*
- **Module layout:** a Qt-free package `srim/mcp/` (server, tool definitions, the headless backend, the app client side of the socket protocol, the ask-first rules and estimates) and a Qt module in `srim/app/` for the socket server, the activity panel, the confirm dialog and the connect dialog. The Qt-free modules go on `tests/test_no_qt.py`'s import list. *(Claude's call.)*

## Tools

The builder designs the exact tool set. It must cover, in both modes:

- **Status:** mode, pysrim2 version, whether SRIM is usable (doctor-style checks), the current setup's path and problems.
- **Setup:** read the whole setup (in the `RunSpec.to_dict()` layout); change it, both by whole sections and by key paths in the `--set` style; new/open/save a setup. Problems come from `RunSpec.from_dict`, as in the app.
- **Help with physics input:** look up elements and isotopes (`srim/core/isotopes.py`), compounds with densities (`compounds.yaml`) and user materials, so "SiO2" or "N15" resolve without guessing.
- **Runs:** estimate a run; start it (single run or scan, with parallelism chosen by the server's defaults unless the agent asks, subject to "Ask first"); status and progress; pause, resume, stop; list and open earlier runs.
- **Results:** summaries (e.g. `implant_summary`: mean depth and straggle per layer), depth profiles and other tables as data with row caps (never a whole big output; reuse `PLOT_ROW_CAP`/`max_rows`), and plots from the Results tab's catalogue (`srim/app/plots.py`). Headless mode saves an image and returns it (as MCP image content and as a path). App mode shows the plot in the Results tab and also returns the image, so the agent can see what the user sees. *(Claude's call.)*
- **Export** (Parquet/HDF5/CSV through `srim/export.py`) and **Save results**, subject to "Ask first" when replacing files.
- **Undo/redo** in app mode. The tool list is the same in both modes (no list changes when the mode switches); an app-only tool called headless returns a clear "needs the app" error. *(Claude's call.)*
- **Install:** plan only (what is missing and the commands); running a non-admin step asks first; admin steps are never run.

The pysrim2 skill reaches the agent through the server: a short version in the server's MCP instructions and the full `SKILL.md` as an MCP resource (or prompt). `SKILL.md` gains a section on the MCP server. *(Claude's call.)*

## App changes

- **Agent activity panel:** a dock, hidden until an agent connects (and from the View menu). Each entry: time, client name, what was done in plain words, and the answer to any ask-first request. The log is also written to a file under the data directory (shared with headless mode; each entry marks its mode), with a size limit. *(Claude's call.)*
- **Undo:** each agent tool call that edits the setup is exactly one undo step, labelled as the agent's ("Undo agent: set beam energy"). The undo history gains labels for this. A user edit and an agent edit are in the same history.
- **Editing during runs:** unchanged from 0.12.0: the setup is locked while a run goes; an agent edit during a run is refused with that reason.
- **Confirm dialog** for ask-first requests (see above).
- **Connect an agent** (Help or Tools menu): snippets with a Copy button for Claude Code (`claude mcp add …`), Codex (`~/.codex/config.toml`), Gemini CLI, Cursor/VS Code (`mcp.json`) and a generic stdio entry. The command is the absolute path of the installed `pysrim2` executable. It also offers to install the skill (`pysrim2 install skill`). *(Claude's call: the client list.)*
- **Settings:** the two ask-first limits; a switch to turn the agent socket off.
- **Live updates option** in the Run settings tab.

## Live updates (decided by Arun: an option, off by default)

- Off (default): a single run stays one TRIM run with the saved seed; its `TRIM.IN` and results are those of the scripted run; the Results tab shows the plot when it finishes (as in 0.12.0).
- On: the run is split into batches with seeds derived from the saved seed (`srim/scan/batches.py`, `derive_seed`, `MergedResults`), and the Results tab redraws the merged results after each batch. Statistically equivalent, not byte-identical to a single TRIM run.
- The option is part of the saved setup so a scripted run of the same `run.yaml` reproduces it. *(Claude's call; the builder picks where it lives in the spec, ideally reusing the existing batch machinery.)* Because it changes the results, its batches must never share cache entries with the unbatched run: the existing cache key already covers each batch's ion count and derived seed, so no change is needed there (the point id stays the same; every run gets a new run folder anyway). It applies to headless runs too. The agent can turn it on, e.g. when the user asks to watch the profile build up.

## Constraints

- AGENTS.md rules hold: private wine prefix, admin steps never run without confirmation (here: never run by the server at all), checksum-verified downloads, no-Qt rule, the app's document rule (every edit through `DocumentModel.edit`), runs through `run_scan`, plots never read a whole big output.
- Python 3.11+. Works on Linux, macOS and Windows (app mode and headless).
- The socket and the discovery file are private to the user; the token never appears on a command line.
- Tests never start a real agent, real SRIM (outside `-m srim`) or a network service: MCP tests use the SDK's in-memory client; app-mode tests use pytest-qt with the fake runners already in `tests/app/runners.py`; headless run tests use the existing fake runners (`PYSRIM2_SCAN_RUNNER`).
- Docs: `docs/agents.md` gains the MCP server (connecting each client, the two modes, ask first and its limits, including that the no-elicitation path trusts the agent to ask); `docs/app.md` gains the activity panel, connect dialog and live updates; `docs/cli.md` gains `pysrim2 mcp`; CHANGELOG entries.
- Everything in this document ships together as 0.13.0 (decided by Arun; no 0.13.1 split). The builder may still split the work into several plans (a natural split: the Qt-free server and headless mode first, then the app bridge and panels), released together.

## Left to the builder

- The exact tool names, arguments and result shapes; the socket protocol between `pysrim2 mcp` and the app.
- The run-time stand-in when no rate is known; the confirm timeout; the activity log's file format and size limit.
- Where the live-update option lives in `run.yaml` and how many batches it uses.
- How the connect snippets are kept correct for each client.

## Changes during implementation

These decisions were taken while building the plans and are recorded here so the spec matches the code.

- **Handshake:** the app's hello carries the client's name only. The client's version is written in the activity log, not shown in the app.
- **Agent menu:** the menu holds the Agent activity dock toggle, **Connect an agent…**, the agent settings and the agent socket switch.
- **Undo and redo:** an agent's undo and redo reverse only the agent's own steps (labelled `agent: `). A user's step on top of them refuses the agent.
- **Questions in app mode:** while the app's dialog is open, the agent's other requests wait for the answer, for at most about two minutes (the dialog's timeout). Headless elicitation is unchanged: other tools keep working while the client asks.
- The dialog's modality (window-modal or not) is still open and is not decided here.

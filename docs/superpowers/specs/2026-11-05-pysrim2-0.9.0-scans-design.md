# pysrim2 0.9.0 — Parameter scans, parallel runs and live progress (design)

Status: draft for review · 2026-11-05 · builds on `2026-11-03-pysrim2-design.md` (sections "Scan", "Execution backends", "Progress front ends") and the 0.8.0 APIs (DataFrames, `implant_summary`, `run.yaml`/`RunSpec`, export, chunked parsing).

## Why

People use SRIM for many different questions: mean implantation depth vs. angle at several energies, vacancy density at a given depth vs. energy, sputter yield vs. ion, or large per-ion baselines for Monte-Carlo sampling. Today each of these means hand-writing loops around single TRIM runs, waiting for them one after another, and gluing outputs together. 0.9.0 makes a scan a first-class, flexible object that runs in parallel on one machine, shows what's happening, survives interruptions, and returns one tidy table.

## Goals

1. **General scans:** any `RunSpec` field can be scanned (ion symbol, energy, angle, number of ions, calculation mode, layer thickness/composition, any TRIM setting), as a grid (all combinations) or as explicit points (zipped lists / a table). Defined in Python; also as a `scan:` section in `run.yaml` (same schema as 0.8.0 plus the scan axes).
2. **Extractors — turning outputs into rows:** an extractor is a plain function `f(results: Results, point: ScanPoint) -> dict[str, float | int | str]`; its dict becomes columns of that point's row. Several extractors can be combined. Predefined extractors ship with pysrim2: `implant_summary` (mean depth, depth/lateral/radial straggle, skewness, kurtosis — SRIM definitions), `vacancy_at(depth_nm=…)`, `peak_vacancy_depth`, `sputter_yield`, `backscattered_fraction`, `transmitted_fraction`, `ions_in_layer(layer)`, `energy_to_recoils`. Users can register their own by name (so they work from `run.yaml` too).
3. **How many ions:** two modes per scan (or per point):
   - **fixed** — exactly N ions (e.g. 100 000 for a Monte-Carlo baseline; per-ion tables kept and exportable);
   - **precision target** — run batches of ions (new seed per batch, seeds recorded) until a named extracted value reaches a target relative or absolute uncertainty (e.g. `mean_depth_A` to ±1 %), with a minimum and maximum ion count. The result table reports value ± uncertainty and ions used.
4. **Parallel on one machine (main case):** a local process pool, default `max_workers = os.cpu_count() - 1`, adjustable. Each worker owns a private copy of the SRIM directory (and on Linux a private copy of pysrim2's wine prefix) so runs never collide. Chunked large runs (one point split into batches across workers) use the same pool.
5. **Container backend:** one container per job (Podman/Docker, same image, same command line), selected with `backend="container"`; same results and tables as local.
6. **Cluster (exception, supported minimally):** a scan can be *prepared* into self-contained job folders (each with its `run.yaml`) plus a generated Slurm array script that runs `pysrim2 run-job <folder>` per array task; `pysrim2 scan collect <scan-folder>` builds the same result table. No other scheduler integration.
7. **One tidy result:** `ScanResult.table` (pandas DataFrame) — one row per point: scanned parameters, extracted values (with `_err` columns for uncertainties), `n_ions`, `seed(s)`, status, and the path to the point's folder (outputs + `run.yaml`). `ScanResult.to_parquet/csv/hdf5` (reusing 0.8.0 export). A small plotting helper `ScanResult.plot(x=…, y=…, hue=…)` (matplotlib, optional extra) for one-line plots with error bars.
8. **Live progress, terminal-first (works over SSH):**
   - **default — live plot view:** a terminal-drawn plot of the chosen result filling in (x = first scanned parameter, y = first extracted value, hue = second scanned parameter; overridable via `plot=(x, y, hue)`), error bars shrinking as ions accumulate, plus a compact status strip (done/running/queued/failed, ions, elapsed, ETA);
   - **`--ui dashboard`:** full-screen dashboard — overall panel (counts, total ions, elapsed, ETA, gauge), workers panel (one row per worker: point, ions, ions/s, CPU), sortable scan-points table (params, status, ions, value ± err, target reached?), throughput sparkline, recent warnings/errors; keys: `p` pause/resume scheduling, `q` stop cleanly, `v` switch to plot view, `l` open a failed point's log;
   - **`--ui web`:** the same app served in the browser;
   - **`--ui plain` / `--ui json`:** one status line every few seconds / JSON-lines events (agents, CI, logging to file); automatic fallback to `plain` without a TTY;
   - **Jupyter:** a live-updating plot + status widget in the cell.
   All terminal views redraw incrementally (low bandwidth over SSH) and work inside `tmux`/`screen`.
9. **Robustness:**
   - a point whose SRIM run fails is retried once, then marked failed with its log; the scan continues; failed points appear in the table with status and error;
   - Ctrl-C (or `q`) stops cleanly: running SRIM processes are stopped, finished points/batches are kept;
   - **caching and reruns:** each run is keyed by the SHA-256 of its canonical `spec:` section of `run.yaml` (the same YAML used to regenerate TRIM.IN, so the hash identifies the physics exactly) plus its seed. Re-running a scan reuses every cached point/batch and only computes missing points or extra batches needed to reach a (tighter) precision target. Cache location: the scan folder (default) or a shared cache directory (`PYSRIM2_CACHE`); `pysrim2 scan clean` removes it.

## Non-goals

- Detached/background scans, `scan watch`, reattaching to a running scan — **use `tmux` or `screen`** (decided by Arun: one tool per job). Docs include a short "long runs over SSH" section with tmux commands; pysrim2 only guarantees it works well inside tmux.
- Schedulers beyond a generated Slurm array script; distributed multi-node pools; GPU anything.
- Adaptive sampling of the *parameter space* (e.g. refining angles where the curve bends) — possible later; 0.9.0 adapts only the ion count per point.
- A Streamlit app (the web view reuses the terminal app).

## Anti-goals

- A scan that silently mixes results from different physics (e.g. cache hit for a spec that differs only in a setting) — the cache key must include every field that affects TRIM.IN.
- Parallel workers sharing one SRIM directory or one wine prefix.
- Losing finished work on interruption or a single failed point.
- A UI that blocks or slows the simulations (UI updates run off the workers' critical path).

## Constraints

- Python 3.11–3.15; TUI via Textual (+ a terminal plotting add-on) as optional extra `pysrim2[tui]`; without it, `plain` output. Web view via textual-serve in the same extra. matplotlib for `ScanResult.plot` stays in `[plot]`.
- Private wine prefix rule still holds per worker (copies live under pysrim2's data/cache dir, never `~/.wine` or `$WINEPREFIX`).
- Same spec + seed → identical results on the same platform; cross-platform identity informational (0.8.0 decision).
- Memory: per-ion data for very large runs streams to disk (Parquet chunks, 0.8.0 helpers); the scan table holds summaries only.

## Decided by Arun

- Flexible scans for many use cases; both fixed ion counts (MC baselines) and "enough for a target precision".
- Main target: laptop / workstation / shared server, parallel across cores (e.g. 32); Slurm supported as the exception.
- Custom extractor functions returning a row, plus predefined ones.
- Live plot as default view; a full dashboard as the alternative; both terminal UIs usable over SSH.
- Reruns via cached hash of the run.yaml spec.
- No detach — document tmux instead.

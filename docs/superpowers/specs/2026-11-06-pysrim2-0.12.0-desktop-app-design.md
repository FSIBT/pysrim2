# pysrim2 0.12.0: desktop app (design)

Status: draft for review · 2026-11-06, updated 2026-11-07 for the released 0.10.0 and 0.11.0 · builds on 0.9.0 (scans, executor events, cache, live views, `pysrim2 doctor`/`install`), 0.10.0 (incoming-particle distributions, exact and binned modes) and 0.11.0 (docs overhaul).

## Why

pysrim2 is a Python library with a CLI and terminal views. Many SRIM users are not programmers and today use SRIM's own Windows GUI. 0.12.0 adds a desktop app that covers the whole path: installing, describing the target and beam, running single runs and scans, watching progress, looking at results, exploring them in a notebook and saving them. An agent (e.g. Claude Code) can drive the app from plain-language requests. The app is a front end to the existing library: everything it does is a `run.yaml`/scan file plus library calls, so results are identical to scripted runs and every setup can be reproduced without the app.

## Goals

1. **Install and first start.** Installable with `uv tool install "pysrim2[app]"` on Windows, Linux and macOS (Windows and Linux are the main targets; macOS is best effort because running x86 Windows software there may stop working). Command `pysrim2 app`. On start the app runs the `doctor` checks; if something is missing it shows a welcome screen (with a link to the docs, see "left to the builder" for in-app help) and a guided setup that installs what is missing through the existing installer steps. The user can choose how SRIM runs: native TRIM.exe (Windows), wine in pysrim2's private prefix (Linux, macOS), or a container (Podman/Docker). The app recommends one per platform. Setup can be reopened from a menu. After setup, the app opens on the geometry tab.
2. **Status bar guidance.** The status bar always says what is missing before a run can start (e.g. "you need to define the ion species, please do …"). Messages are clickable and jump to the field.
3. **Geometry tab.**
   - A to-scale cross-section of the target with the beam coming in from the left; layers too thin to see at scale (e.g. 10 nm on 1 cm) are drawn at least a few pixels wide and marked as not to scale (real thickness on hover). The beam arrow shows the incidence angle.
   - An editable table beside it: one row per layer with name, elements (stoichiometry), density and thickness (unit selector Å/nm/µm/mm). Layers can be added, removed and reordered by dragging. Selecting a row highlights the layer in the picture and vice versa.
   - Element selection: a periodic table pops up; clicking an element opens a small popup listing its stable isotopes and a **natural** button (natural isotope mixture = SRIM's standard element and mass). A single isotope becomes that element with the isotope's mass (SRIM supports one mass per target element).
   - Predefined materials: pick a material (Si, SiO₂, Au, Kapton, …) to fill elements, ratios and density, still editable. Users can save their own materials.
   - Invalid or missing values are flagged in the table and explained in the status bar.
4. **Beam tab.**
   - Ion chosen with the same periodic table + isotope popup; energy, angle, number of ions.
   - Distributions (0.10.0) for energy and angle first, and also for what 0.10.0 can distribute besides (azimuth, entry position y/z/depth): every shape 0.10.0 supports (fixed, Gaussian, uniform, triangular, log-normal), a Python function (`python:<module>:<name>`), or a measured histogram loaded from a file (preview before accepting), with truncation where 0.10.0 allows it. Each distributed parameter shows a small plot of the distribution; after a run the sampled values are drawn on top.
   - Exact (TRIM.DAT) or binned mode is a choice in this tab, with a default chosen by the app and a one-line explanation; in binned mode the bins appear on the plot and each bin is a point in progress and results. Limits are flagged in the status bar, with the message of the library's `SpecError` (e.g. at most 99,999 ions in exact mode, too many bins in binned mode).
5. **Parallel runs.** When a run looks long, the app asks whether to run it in parallel and offers a worker count (default cores − 1), batch splitting and, for big jobs, the container backend.
6. **Progress tab.** The content of the 0.9.0 dashboard: overall status (counts, ions, elapsed, ETA), workers, points table, recent warnings/errors, with pause/stop buttons and opening a failed point's log. It is fed by the executor's event stream.
7. **Results tab.**
   - One tab with a grouped list of plots on the left ("Depth profiles", "Ion distributions", "Damage", "Scan", …) and the selected plot on the right. Plots that need outputs this run did not produce are shown greyed out with the reason on hover (e.g. "needs collision details; enable 'Collision output'"); plots that can never apply to this kind of run (scan plots for a single run) are not shown.
   - During a run only the visible plot updates, every N seconds (N configurable); switching plots draws the new one once immediately. Plots can be popped out into their own windows (also updated while visible) to compare side by side.
   - Each plot has a toolbar: zoom, log scale, export to PDF/PNG, copy/save the data behind it.
   - Scans: a summary plot (an extracted value against a scanned parameter, coloured by a second parameter, error bars from the precision estimate; x, y and colour chosen from drop-downs; fills in during the scan) and overlays of per-point plots (depth profile etc.) for points chosen with a point picker or a filter, one colour per point with a legend. Numeric colour parameters use a sequential colour map with a colour bar; categorical ones distinct colours; every curve also has its own line style or marker. A scan point keeps the same colour in every plot. With more than about a dozen curves the app suggests a filter.
8. **Notebook.** Menu entries **Start marimo** (default) and **Start Jupyter** create a starter notebook in the run folder (first cell loads the current results, plus an example plot) and open it in an embedded web view. The notebook server runs in its own process, separate from the simulation; it reads the run folder. During a long run what the notebook loaded is a snapshot: a banner says when new results exist and reloading re-runs the loading cell; marimo additionally gets a "follow the run" switch that re-runs the loading cell and its dependents every N seconds. Notebooks are saved with the run. Notebook export to PDF: marimo's own export; Jupyter's needs LaTeX or a headless browser, offered as an optional setup step.
9. **Saving and export.** Save results in the formats the library supports (Parquet, HDF5, CSV, plus the raw SRIM outputs and `run.yaml`), with user-chosen output file names and locations. Plots export to PDF (and PNG); notebooks to PDF (goal 8).
10. **Recent runs.** A menu listing recent run and scan files (`run.yaml`/scan files) to switch between; opening one restores its geometry, beam, settings and results.
11. **Agent.** During setup (optional step) or later from a menu, the user can connect an agent (Claude Code or any agent that speaks MCP). The app runs a local MCP server exposing its actions (edit target and beam, set scan and run options, start/stop runs, read results and plots) and gives the agent the pysrim2 skill. A chat panel docked in the window takes plain-language requests; the agent changes things in the app directly (no per-step approval) and the tabs update as it works. Every agent change goes into the normal undo history and an activity log; runs it starts appear in the progress tab and can be stopped there. For long runs the agent decides about parallel execution itself with sensible defaults (no dialog). The agent runs under the user's own account; the app stores no keys.
12. **Look.** Qt 6 via PySide6. Dark and light mode follow the operating system by default, with a System / Light / Dark switch in the settings.

## Stages (decided by Arun)

- **0.12.0:** setup and doctor screens, status bar guidance, geometry, beam (with 0.10.0 distributions), run settings, the parallel-run prompt, progress, results and plot export, saving/export, recent runs, dark/light mode (goals 1-7, 9, 10, 12).
- **0.12.x:** notebooks — Start marimo / Start Jupyter, embedded view, reload banner, marimo "follow the run", notebook PDF export (goal 8).
- **0.13.0:** the agent — MCP server, chat panel, skill, undo/activity log for agent actions (goal 11). What the agent may do unattended (installer steps that need admin rights; a cap on runs it starts by itself) is decided when 0.13.0 is designed.

## Non-goals

- Replacing the library or CLI: the app adds no physics or run logic of its own.
- A web app or hosted service (the notebook view is a local embedded web view only).
- Editing SRIM's internal databases (stopping powers, element tables) beyond user-defined materials.
- Multi-user or remote control of a running app beyond the local agent connection.

## Anti-goals

- The app producing results that differ from the same `run.yaml` run through the library or CLI.
- Agent actions that are invisible or cannot be undone.
- A frozen or sluggish UI during runs (plots and the notebook must not slow the workers).
- A crash in the notebook or agent taking the simulation down.

## Constraints

- PySide6 (LGPL; fits pysrim2's MIT licence), optional extra `[app]` with what 0.12.0 needs (PySide6, matplotlib); the notebook tools (marimo; Jupyter optional) come with the 0.12.x notebook feature. `import srim` and the CLI never import Qt. Installable with `uv tool` on Windows, Linux, macOS; Python ≥ 3.11 like the rest of pysrim2.
- Private wine prefix rule, container rules and admin-rights confirmation from AGENTS.md apply to the setup screens.
- The app works without network access once installed (except docs links and the agent).

## Decided by Arun

- Qt 6 (PySide6 is fine); dark/light following the OS with a switch.
- The app stays an optional `[app]` extra, not part of the normal install, because PySide6 would make every install about 100 MB larger; the container image installs without it and stays small (2026-11-07).
- Welcome screen with docs link, then a guided install depending on platform, letting the user choose native/wine/container.
- Status bar help for missing steps.
- Geometry: drawing with a minimum visible width for thin layers, editable table, reorder/add layers, periodic table popup with isotopes and a "natural" choice, predefined materials.
- Beam: same element/isotope picking; distributions for energy and angle — all 0.10.0 shapes, Python functions, measured histograms — with visualisation.
- Long runs: prompt to run in parallel.
- Results: one tab with a list of plots, unavailable plots greyed out or hidden, only the visible plot updates every N seconds; scans plotted with colours.
- Notebook: marimo by default, menu entries to start marimo or Jupyter, embedded web view; exploring results and combining with own data.
- Save data in several formats with chosen names; export plots and notebooks to PDF; recent runs menu.
- Agent: connectable during setup or later, gets the skill, changes things in the app directly; tabs update.

## Calls made after the builder check (Claude's, marked as such)

- **Library changes are allowed** where they are generally useful (isotope and material data, run-time estimate, model helpers); the app adds no physics. *(Claude's call)*
- **Where things run:** like the 0.9.0 terminal views, the app runs `run_scan` in a background thread of the app process (the SRIM workers are already separate processes); the notebook server is a separate process; the agent connects to a local MCP server inside the app. A notebook or agent crash cannot stop a run. *(Claude's call)*
- **Source of truth:** the app edits a `RunSpec`/scan definition; everything it can set must be expressible in `run.yaml`/scan files. Python-function distributions are stored as `python:<module>:<name>` references (as extractors in 0.9.0); measured histograms are copied into the run folder and referenced by relative path; user materials and isotope choices end up as plain elements/masses in the spec. *(Claude's call)*
- **Notebook view:** QtWebEngine is part of the `[app]` extra; if it is unavailable the notebook opens in the system browser. *(Claude's call)*
- **Run settings tab:** a third editing tab for calculation type (quick / full cascades / monolayer), which outputs to write (collisions, sputtered, transmitted, ranges, …) and other TRIM settings. SR stopping tables come later. *(Claude's call)*
- **Isotopes:** a layer may contain several isotopes of one element as separate element entries with their own masses (TRIM.IN allows this); "natural" uses SRIM's default element mass, so results match scripted runs. *(Claude's call)*
- **Undo and editing during runs:** one undo history for user and agent edits; the setup is locked while a run is going (a run uses a snapshot of the spec); results stay attached to the spec they were made with, and editing afterwards marks them "from the previous setup". *(Claude's call)*
- **Testing:** headless GUI tests with pytest-qt (offscreen platform) in the existing CI matrix; no screenshot tests. *(Claude's call)*
- **Recent runs:** reopening shows the saved setup and results read-only until edited; a moved or deleted folder is shown greyed with a message. *(Claude's call)*
- **Settings and user data** (recents, materials, theme) live under the pysrim2 data directory from `srim/paths.py`, shared with the CLI where it makes sense. *(Claude's call)*
- **Depends on 0.10.0:** the distribution UI follows `srim/beam/` as released in 0.10.0 (the shapes, exact/binned modes, `check_beam`); the app validates through the library, not its own rules. *(Claude's call)*
- **Docs (0.11.0 layout):** a new "Desktop app" page goes into the Guides section of `docs/index.md`; the front page's Python card mentions `pysrim2[app]`; the welcome screen links to `https://pysrim2.readthedocs.io`. App screenshots go into the gallery as `make.py` entries that draw the windows offscreen (Qt `offscreen` platform, `QWidget.grab()`), from fixtures, no SRIM. *(Claude's call)*
- **Plans:** 0.12.0 is built from three plans in order: (1) app shell, setup and doctor screens, status bar, settings, dark/light; (2) geometry, beam and run-settings tabs; (3) running (parallel prompt), progress, results and plot export, saving, recent runs. Each ends with a working app. *(Claude's call)*
- **Also in 0.12.0:** the dashboard fix already on main (a live view is drawn only once its screen has mounted). *(Arun: no 0.11.1)*
